## 第 1 轮 · 三档分类怎么和现有六因子打分共存？

**【苏姐】** 先把话摆在桌面上：用户要的是「紧急 / 日常跟进 / 提醒」三个词。我的第一反应是 —— 三档取代分数。理由是认知负担。现在卡片右上角挂一个 `82.1`，左侧还有 tier-red/orange/yellow/green 四条色带，展开还有六因子明细。一个刚转岗半年的人打开看板，第一眼要处理三套优先级语言：分数、四色、P0-P3。这是典型的「我们把内部实现泄露给用户」。三个中文词就够了。

**【小采】** **我不同意。** 你把分数砍了，第一天就出事。

我给你一个真实场景：今天早上「紧急」这一档里躺着 7 条 —— 三拼腰封逾期 2 天（日配，库存半天）、纸盒 A 今天最晚下单日、隔板加急单、两笔今天到货要盯、一笔今天要催付款、一条差异要定性。七条都叫「紧急」，她先打哪个电话？

这就是 SPEC-procurement §〇 写的第二个痛点原话：**"都急，就等于都不急，最后按谁先给我打电话排序"**。三档解决的是"这是什么性质的事"，它解决不了"七件同性质的事谁先做"。分数解决的正是后者。你砍掉分数，等于把她推回按来电顺序干活。

**【苏姐】** 那反过来，用分数取代三档呢？分数已经能排全序了，三档是冗余的。

**【小采】** 也不行，理由更硬：**分数不可解释成一句人话。** 82.1 分是什么意思？她要展开看六因子才知道。但「紧急」三个字她不用展开就知道要干嘛 —— 现在就动。而且分数有一个致命的表达缺陷：**它把不同性质的事压成同一根轴。** 一条「等生产回话的拦截确认」和一条「今天必须打的催货电话」，分数可能都是 60，但它们要她做的事完全不同 —— 前者是"我推出去了，等回音"，后者是"我现在拿起电话"。用户列的三档恰恰就是按**她的动作性质**分的，不是按紧迫度分的。你看他的原话：「审批流程的属于提醒」—— 审批流程急不急？可能很急，但那件事**不由她推进**。这是性质，不是刻度。

**【苏姐】** 这句我认。那就把它讲清楚：**三档是语义分区（她现在该拿什么姿势对待这件事），分数是档内排序（同姿势的事谁先做）。** 两件事，两个字段，谁也不吃掉谁。

但我要提一个反对：**我不同意**你刚才顺口说的"三档只是给人看的颜色"。如果三档只是显示层的装饰，它一定会漂 —— 今天某个开发觉得 T3 应该算紧急，就改一行 UI，明天没人知道为什么变了。三档必须是**可程序判定、有唯一入口、有单元测试**的一等公民，落成 `band` 字段，判定函数只有一份。它和 score 是并列的两个计算产物，不是 score 的衍生显示。

**【小采】** 同意，而且判定规则要能逐条对着采购的真实触发条件念出来，不许出现"视情况而定"。我来定业务规则，你来定形状。

**【苏姐】** 那形状我先定死三条：

1. 判定**按顺序短路**：urgent → follow → notice，第一条命中即止。一张卡只能有一个档 —— 和「一张卡只能有一个家」是同一条铁律的延伸。
2. **兜底必须存在**：任何一张卡都能落到 notice，永不出现"没档"的卡。
3. **顺序稳定**：判定只依赖卡片自身字段 + 当日 bizDate，不依赖其它卡的状态，否则她关掉一张卡，别的卡的档就跳了。

**【小采】** 那业务规则我按用户原话逐条翻译。他说的四种紧急是：「今天就要下单不然来不及的、加急的、今天送到的、今天要催着付款的」。这四个在采购语言里是四类完全不同的触发：

- **今天就要下单** = `最晚下单日 ≤ 今天`（SPEC §3.1 f_time 的 slack ≤ 0），或者已经过了 → T1-B
- **加急** = 加单表 `is_urgent = 1`，或者日配件覆盖天数见底（水位 < 3 天，SPEC §2 T10）
- **今天送到** = 承诺交期 = 今天（这天不盯，货到了没人点数，SPEC §1 13:30 那一段）
- **今天要催着付款** = 这个现在**代码里没有** —— T11 对账是月度的，不进泳道。但用户明确点了它，说明她的一天里真有这件事。要新增一类。

**【苏姐】** 新增一类要走等价交换。你换掉哪个？

**【小采】** 换掉 T11 进看板的可能性 —— 我原来的规格里 T11 是"月度自动生成"，那个粒度进不了日看板。改成 `T13_payment`：**只在付款/开票节点撞上今天或明天时才生成一张卡**，其余时间不出现。这样它不是新增一整类月度任务，是把 T11 的日粒度切片拿出来。T11 本体仍然不进泳道。

**【苏姐】** 接受。那冲突时谁赢？举个具体的：一张 T5 在途卡，承诺交期是今天（按你的规则 → 紧急），但它的 score 只有 31 分（非日配、库存够 20 天、供应商准交率 0.95）。它该在哪？

**【小采】** 在紧急。**band 赢。** 理由：今天到货这件事，不盯就是货躺在门口没人点数，SPEC-procurement §1 那句"实物动，单据动，拖到明天仓库那边就变成我记得好像收过"。这个后果和库存够不够 20 天无关。分数低只说明它在紧急档里排最后 —— 她今天最后一个处理它，但今天必须处理。

**【苏姐】** 反过来的情况我要留一个通道：score ≥ 175 的卡（也就是命中了 score.ts 里 R1 置顶 +100、基础分还有 75 以上的），那是"已逾期 + 日配/已断料"的组合。这种卡如果因为 kind 判定落进 follow，我不能接受。给一条**唯一的反向改写通道**：`score ≥ 175 → 强制升 urgent`，并且这条改写必须写进 `reasons[]`，卡片上明写"这条本来算日常跟进，是分数把它顶上来的"。

**【小采】** 可以，但**只准这一条反向通道**，不许再加第二条。多一条，band 就变成 score 的函数了，那就退回你一开始说的"分数取代三档"。

**【本轮结论】**
三档与分数**各管一件事，字段并列**：`band`（语义分区，决定她拿什么姿势）由 kind + 硬条件短路判定；`score`（0~200，公式不动）只做**档内排序**。冲突时 **band 赢**，唯一例外是 `score ≥ 175` 可反向把卡升进 urgent 且必须在 reasons 里留证。`P0/P1/P2/P3` 的 `level` 字段**保留在数据层**（日清统计、导出、调试用），**从 UI 全面下线**，卡片四色 `tier-*` 改为三档 `band-*`。新增 `T13_payment`，等价交换：T11 月度对账本体明确不进泳道。判定规则全表见 §最终方案 · 2。

## 第 2 轮 · 泳道改成「需求 / 待下单 / 在途 / 入库」，"等确认"去哪了？

**【苏姐】** 用户列的四道里没有「等确认」。现有 `confirm` 泳道要么消失，要么并进别处。我的方案是并进「在途」：从产品视角，`confirm` 和 `transit` 的用户动作是同一个 —— 都是打电话找供应商要个准话。合并之后泳道数不变，代码改动最小，卡片按 kind 区分标题就够了。

**【小采】** **我不同意。** 而且这是今天最重要的一次不同意，因为它直接对着我规格里标了三颗星的那个点。

SPEC-procurement §5 状态机 S3 那一格我原话写的是：**"全流程最常被跳过的一步 —— 新人以为发出去就算下完了"**。SOP 03 第三步第 4 点：**"回签前订单只是你的一厢情愿"**。口诀是**"无单不采，无签不认"**。

你把未回签放进「在途」，产品语言上你就是在告诉她：这批货已经在路上了。**它不在路上。** 供应商可能根本没看到这张单，可能看到了但排不进产线，可能数量和你写的不一样。我见过太多次：新人在跟单表里把未回签的单当在途算，算净缺口时把它当"有效在途"扣掉，结果缺口算小了，到需求日两头空。SPEC §7 盲区清单第 2 条就是这个：**"有效在途 ≠ 在途"**。

**【苏姐】** 那你放哪？「待下单」？单都下了还叫待下单，这也别扭。

**【小采】** 就放「待下单」，而且一点都不别扭 —— 因为**「下单」这个动作在采购语言里本来就不是"点了保存"，是"拿到供应商书面确认"**。SOP 03 的下单自查清单最后三条：「已审核 + 已发供应商 + 已要求回签」「已登跟单表」「已回复需求部门」。这三条没做完，这单在采购的账本上就是没下完。

我再给你一个更硬的判据 —— **按"谁在动"分道**：

| 泳道 | 现在是谁在动 | 她的姿势 |
|---|---|---|
| 需求 | 生产 / 计划 / 领导 在动 | 我推出去了，等别人一句话 |
| 待下单 | **我**在动 | 这件事的进展完全取决于我今天做不做 |
| 在途 | 供应商 + 物流 在动 | 我只盯、只催，不做 |
| 入库 | 仓库 + 质检 在动 | 我核对、我定性，实操是他们 |

按这个判据，未回签百分之百落「待下单」—— 因为**要回签是她的活，没人会主动给她**。放进「在途」，她的姿势就从"我该催"变成"我该等"，这一字之差就是 SPEC 里那三颗星。

**【苏姐】** 这张"谁在动"的表我服，它比我原来那套 stage 命名干净得多 —— 它同时解释了泳道的边界、卡片的语气、和升级动作找谁。收进最终方案。

但我要反对另一件事：**我不同意** T10 日配水位巡检放进「需求」。它现在在 `order` 泳道，你要把它挪到「需求」。可日配巡检的产物是"该不该补货"，这是她自己判断、自己下单，没有别人在动 —— 按你自己的表，它该在「待下单」。

**【小采】** 你把 T10 的产物看错了。T10 的产物**不是一张单，是一个数字** —— 今日覆盖天数。SPEC §2 T10 的完成判定原话：「5 件全部有当日水位数字，且 < 3 天的每一件都有一个已执行的动作（调拨 / 催货 / 通知生产）」。它是**需求的来源**，不是一条已经定了量的单。真要下单，它会**派生**一张 T1 落到「待下单」—— 两张卡，两个家，不冲突。

而且放「需求」有一个实际好处：她早上 8:30 的第一个动作（SPEC §1 开机三件事第 1 件）就在第一条泳道的最上面，视线不用跳。

**【苏姐】** 派生这个说法我接受，那 T1-B 呢？按你的规格 T1-B 是 T1 的分支，现在 `STAGE_OF` 里它跟 T1 一起在 `order`。

**【小采】** T1-B 挪到「需求」。理由同一条判据：T1-B 的动作对象是**生产和领导**（"推迟 X 天还是先到一半先开线，您定一个"），等的是别人一句话。它和 T3 拦截是同一性质 —— 这个料到底还要不要、按什么条件要，**需求本身还没定死**。SPEC §2 T1-B 完成判定原话就是「有一条书面结论」，不是「已开单」。

**【苏姐】** 那「需求」这条道就有四类：T3 拦截、T1-B 来不及、T2 无授权加单、T10 水位。这四类有一个共同的行为特征 —— **她今天能做的只有"发出去 + 记下截止时间"，闭环不由她说了算**。这个特征值得直接写进泳道的 hint 文案，让她别为这道里关不掉的卡焦虑。这也正好接上反指标"卡片积压率"：需求道的卡天然积压率高，统计积压率时**这一道要单独算**，不然反指标会误报。

**【小采】** 这个补充很实在。那还有一个边界要说死：**「入库」道从哪里开始？** 我的口径：**货到本地即入库道**，不管有没有点数、有没有录单。T6 明日到货预告虽然发生在货到之前，但它是入库这件事的第一步（SOP 04 第一步），且完成判定是"仓库回执"—— 仓库在动，符合判据。所以 T6 在入库道。

**【苏姐】** 同意。最后一件事：`Stage` 的字符串枚举值要改。`order` → `to_order`、新增 `demand`、`confirm` 消失、`transit`/`inbound` 不变。这是破坏性变更，要迁移 `board_tasks.stage`，历史 done 卡也得迁，否则日清统计和导出全错。写进给老架的清单。

**【本轮结论】**
四泳道按**「现在是谁在动」**划界：**需求**（别人在动，她只能推出去+定截止）/ **待下单**（她在动，从算完净缺口到拿到书面回签）/ **在途**（供应商+物流在动）/ **入库**（仓库+质检在动）。
**「未回签」归「待下单」** —— 依据 SOP 03「回签前订单只是你的一厢情愿」与口诀「无签不认」，放「在途」会让她误以为货在路上并把它当有效在途扣减净缺口（SPEC §7 盲区第 2 条）。
T1-B 与 T10 从 `order` 迁到 `demand`；T10 覆盖天数 < 3 时**派生**一张 T1 到「待下单」，两张卡两个家。
「需求」道积压率**单独统计**，不并入全局反指标。`Stage` 枚举值变更为破坏性变更，需数据迁移。映射全表见 §最终方案 · 1。

## 第 3 轮 · "每个流程里对应着一个操作"—— 一张卡只能有一个动作吗？

**【苏姐】** 用户原话「每个流程里对应着一个操作」。我读出来的意思很明确：**一张卡 = 一个动作**。现在 TaskCard 展开后是 3~6 个 checkbox，卡片底部还有三个按钮（怎么做 / 问采姐 / 干完了）。一张卡上最多能点 9 个地方。这不是"一个操作"，这是一张小型表单。

我的方案：把 steps 全部降级成展开区的**只读做法说明**（不可勾选），卡面只留一个主按钮。完成 = 点主按钮。

**【小采】** **我不同意，而且这个不同意的代价是会出事故。**

steps 不是"做法说明"，是**防跳步装置**。我给你看 SOP 03 第一步下面那行红字，一字不改：**"🔴 新手最常见事故就是跳过 2、3 直接照生产表下单 → 重复采购、库存积压。每次都算，一次都不跳。"**

T1 下单卡的 s1 是什么？「核算式输入：可用量取的是"可用"不是"现存"？在途里逾期未决的剔干净了？」这一步不勾，她就直接去 U8 开单了。你把它变成"只读说明"，就等于把这行红字变成了一段没人读的小字。SPEC §7 盲区清单第 1、2 条 —— **"可用量 ≠ 现存量"、"有效在途 ≠ 在途"** —— 就是靠这一勾拦住的。

**【苏姐】** 那按你的逻辑，六个 checkbox 全都是防跳步装置，一个都不能少 —— 那"一个操作"这句需求就等于没做。用户为什么会提这句？他看到的现状就是"卡片太多东西要点"。

**【小采】** 他提的是**主次不分**，不是数量。你看现在 T1 卡的五步：s1 核算式（防事故）、s2 MOQ 三选一（要她拍板）、s3 交期倒推（信息展示，她啥也不用做）、s4 去 U8 开单（真正的动作）、s5 审核+发出+回填单号（真正的动作的收尾）。

这五步里，**s3 根本不该是一个 checkbox** —— 它是一句结论，不是一个动作。s4+s5 合起来才是"那一个操作"。s1、s2 是这个操作的**前置条件**。

**【苏姐】** 那模型就出来了，而且它能同时满足两边：

**主操作（primaryAction）+ 闸门步（gate）+ 参考步（hint）**

- 每张卡**有且只有一个** `primaryAction`。卡面底部只有它一个主按钮，文案是动词 + 凭据要求，例如「已在 U8 开单 →」，点下去弹一个只有 1~2 个字段的小输入（订单号）。
- `gate` 步：必须勾完，主按钮才从灰变亮。**这是把你的防跳步装置从"她自觉去勾"升级成"不勾就动不了"** —— 比现在还硬。
- `hint` 步：展开区的做法说明，不可勾、不阻塞，纯参考。s3 这种归这儿。
- 「干完了」这个按钮**消失**。完成判定从"她自己判断+点一下"，改成 `所有 gate 已勾 && primaryAction 已执行且凭据字段非空` → 自动 done。

**【小采】** 主按钮亮不亮这个设计我很喜欢，它把"跳步"这件事从"她违反 SOP"变成"她物理上做不到"。但我要提一个反对：**我不同意** gate 步数不设上限这件事 —— 你没说上限，那开发一定会把所有防跳步的步骤都标成 gate，最后回到六个 checkbox，只不过现在还锁着按钮，体验更糟。

**【苏姐】** 那我给硬约束：**gate ≤ 2 条**。超过 2 条就不是"一个操作"了，这是产品侧的红线，卡片生成时校验，超了直接构建失败。

**【小采】** 2 条够用，我核对一遍最狠的几张卡：
- T1 下单：gate = ①核算式输入 ②MOQ 三选一（仅当低于 MOQ 时存在）。正好 2 条，且第 2 条是条件性的。
- T8 逾期催货：gate = ①已通知生产（SPEC §2 T8 完成判定原话"只打了电话没通知生产 = 未完成"）。1 条。
- T9 差异：gate = ①已定性（四选一）②已双向通知（供应商 + 仓库）。2 条。
- T2 加单：gate = ①授权凭据已挂。1 条。

都在 2 条以内。这个约束逼着我们只保留真正会出事的那一两步，其余降 hint —— 这其实是好事。

**【苏姐】** 那 `doneRule` 那句话还留不留？它现在是纯文案。

**【小采】** 必须留，而且现在它终于有了程序对应物。以前 doneRule 是一句她自己对照的话，现在它变成 **gate 清单 + primaryAction 凭据字段的人话版本**。两者必须一致 —— 卡片生成时校验：doneRule 里提到的每一个可验证事实，都要能在 gate 或凭据字段里找到落点。找不到的，说明我们写了句空话。

**【苏姐】** 这条校验我加进构建期检查。另外 `[怎么做]` 按钮也可以砍了 —— 它现在的行为就是展开卡片，和点标题一样，是个冗余按钮。卡面就剩：主按钮 + `[问采姐]`。两个。

**【本轮结论】**
卡片动作模型 = **一个主操作 + ≤2 条闸门步 + 若干参考步**。
`primaryAction`：每卡唯一，动词 + 凭据字段（点击后弹 1~2 个输入格）。
`gate`（≤2 条，硬约束，超限构建失败）：不勾完主按钮保持禁用 —— 把防跳步从"自觉"升级为"物理不可跳"。
`hint`：不可勾、不阻塞的做法说明，纯信息（如"交期倒推结论"）。
「干完了」按钮**取消**，完成判定改为程序判定：`所有 gate 已勾 && primaryAction 凭据字段非空` → 自动 `done`。`[怎么做]` 按钮取消（与点标题重复）。`doneRule` 保留为人话文案，但构建期校验它必须与 gate + 凭据字段一一对应，不许写空话。

## 第 4 轮 · 可编辑字段的边界在哪？

**【苏姐】** 我先把我自己定的铁律念出来，免得被说我临时改口。SPEC-product §7 R2 原文：**到货量 / 入库量 / 订单数量三个字段永久只读**，可写的只有跟进记录与步骤勾选。理由是 SOP 05 那句"以 U8 为准，不维护第二套账"。

现在用户要"支持写基本的备注、货码、供应商、日期"。备注我毫无意见 —— 那本来就是过程记录。日期要分类看。**货码和供应商我反对。**

**【小采】** 你先说反对的理由，我再说我的场景。

**【苏姐】** **我不同意货码可写**，理由是它是主键。`material_code` 在整个数据模型里是连接生产表、物料表、库存、订单行、任务卡的唯一锚点（SPEC §6.1 原话："存货编码是全公司唯一语言，下单认编码不认名称"）。她在卡片上改一下货码，这张卡就从一个物料跳到了另一个物料 —— 打分因子（日均用量、覆盖天数、供应商准交率）全部跟着变，而且是**静默地变**。她昨天记住的那张卡今天变成了另一件事。

供应商同理：`onTimeRate` 是打分因子，改供应商就是改分数。**任何一个可写字段一旦参与打分，公式就不可信了** —— 她改一下字段就能把一张卡顶到第一位，那这套"分数必须能被质疑"的设计就白做了。

**【小采】** 你的理由我全部接受，但你的结论我不接受。**我不同意"货码和供应商一律只读"** —— 因为她真实工作里有两个场景，只读会让她卡死在看板外面：

**场景一：编码未命中。** SPEC §2 T3 的一条触发条件就是"存货编码在 152 项里查不到"。生产表上写着一个编码，她一看就知道是生产的人手打错了（少一位，或者写成了旧编码）。她已经打电话跟生产核实过了，正确编码是 XXX。现在她拿这个正确编码没办法 —— 只读，她只能去改生产表原文件再重新导一遍。**为了一个字，重走一遍导入流程**，这就是 SPEC-product R1 说的"数据入口摩擦致死"。

**场景二：换供应商。** T1-B 来不及了，原供应商赶不上，她启用备选供应商（SOP 03 场景 2 第二步）。这个决定是她当场做的，U8 里那张单还没开，物料档案上的主供应商还是原来那家。她要在卡上记下"这单走备选"，只读就记不了。

**【苏姐】** 你这两个场景我都认。那解法就不是"能不能写"，是**"写在哪一层"**。

关键洞察：这两个场景里她写的东西，**性质不是"修正 U8 的数"，是"记录我的判断"**。所以不该覆盖原字段，该新开一层：

**三层数据模型**
1. **事实层（只读，来源 U8/生产表）**：`materialCode` `qty` `receivedQty` `stockedQty` `price` `available` `poStatus` `needDate`。每个字段旁常驻来源戳（`U8 报表 · 09-04 08:12`）。**永不可写，永不被覆盖。**
2. **判断层（可写，人工核定）**：`materialCodeFix` `supplierOverride` `promiseDate` `etaDate` `trackingNo` `nextActionAt` `blockedBy` `escalatedTo`。写了不覆盖事实层，**并列显示**。
3. **过程层（可写，自由）**：`note` 备注、`taskEvent[]` 跟进记录（日期 + 对方 + 原话 + 结论）。

**【小采】** 三层这个划法干净。那并列显示怎么显示？她会不会看着两个数更懵？

**【苏姐】** 冲突时的显示规则，一条硬规则，不许有第二种样式：

```
货码  11101011  ⓘU8 · 09-04 08:12
      ↳ 你核定为 11101016 · 09-04 10:23   [用这个] [撤回]
```

三个要点：① **原值在上，永远不动**；② 人工值缩进一行，带时间戳；③ 有一个 `[用这个]` 按钮 —— 点了之后**不改这张卡**，而是生成一张 `T14_conflict` 核对卡进「需求」道，内容是"去 U8 / 找生产把物料表这一行改对，改完重新导入"。**小采永远不替她改 U8，也不替她改自己的数据源。**

**【小采】** 这个 `[用这个]` 生成一张核对卡的设计，正好把 SPEC-product 铁律 5 那句"她背的锅，必须由她按的按钮产生"落地了。同意。

那打分怎么办？判断层的字段参不参与打分？

**【苏姐】** 默认：**判断层字段一律不参与打分**。有一个例外，我想听你的判断 —— `promiseDate`。

**【小采】** `promiseDate` 必须参与打分，而且是最重要的那个输入 —— SPEC §3.1 f_time 那一行原话："跟货类用 promised_date"。回签拿到的承诺交期就是在途/催货类任务的最晚动作日锚点，不让它参与打分，整个「在途」道的分数就是假的。

但我给它加一个约束，让你放心：**`promiseDate` 必须带来源标记 `promiseSource`**，三值枚举：

| promiseSource | 什么算 | 参与打分？ |
|---|---|---|
| `signback` | 有回签件（图片/PDF/明确含数量与日期的文字） | ✅ 参与 |
| `verbal` | 电话里对方口头说的 | ❌ 只显示，不参与 |
| `guess` | 她自己按经验估的 | ❌ 只显示，不参与 |

这条规则本身就是在教她 SPEC §7 盲区第 16 条：**"回签才算承诺，'好的''收到'不算"**。她填 `verbal` 的时候，界面告诉她"这个日期不会进打分，因为它还不是书面承诺"—— 这比采姐讲十遍都管用。

**【苏姐】** 漂亮，这是把业务纪律变成了产品机制。收。那 `qty` 呢？用户没说要写数量，但我预感会有人问。

**【小采】** 死守只读。理由一句话：**订单量 / 到货量 / 入库量这三个数，是三单匹配的三条腿**（SOP 01 §1.3）。她一改，付款前的三单匹配就没有基准了，这是财务风控底线。这条不做任何妥协。净缺口 `netGap` 是系统算的，也只读 —— 但它的算式必须可展开（现有 ⓘ 已实现，保留）。

**【苏姐】** 最后一个：`needDate` 需求日期。用户说要写"日期"，这个算不算？

**【小采】** 不算。`needDate` 来自生产表，是生产给我的需求。她改它 = 她替生产改需求。这是越权（SOP 01 §4 红线第 2 条"不私自承诺"的同类）。真要改，走 T3 拦截卡问生产要一句书面。可写的日期只有三个：`promiseDate`（供应商给的）、`etaDate`（物流给的）、`nextActionAt`（她给自己的）。**判据：这个日期是谁承诺的，就只有拿到那个人的承诺才能写。**

**【本轮结论】**
数据分三层：**事实层（只读，来源 U8/生产表，带来源戳）/ 判断层（可写，不覆盖事实层，并列显示）/ 过程层（可写，自由）**。
只读永久名单：`materialCode` `qty` `receivedQty` `stockedQty` `netGap` `price` `available` `poStatus` `needDate`。
可写名单：`note` `taskEvent[]` `materialCodeFix` `supplierOverride` `promiseDate`+`promiseSource` `etaDate` `trackingNo` `nextActionAt` `blockedBy` `escalatedTo`。
冲突显示唯一样式：**原值在上不动，人工值缩进一行带时间戳**，`[用这个]` 不改数据、只生成一张 `T14_conflict` 核对卡进「需求」道。
判断层字段**默认不参与打分**，唯一例外 `promiseDate` 且必须 `promiseSource = signback` 才计入 —— 用产品机制教会她「回签才算承诺」。字段全表见 §最终方案 · 3。

## 第 5 轮 · "标记该去 U8 哪里查/操作" 怎么落地才不变成噪音？

**【小采】** 用户这句需求我最有共鸣 —— 她的真实卡点从来不是"我不知道要做什么"，是"我知道要开单，但那个菜单在哪儿"。SPEC §7 乙组五条盲区全是系统操作。所以卡片上必须印路径。

**【苏姐】** **我不同意"卡片上印路径"这个说法** —— 至少不能像现在这样印。你看现在 `generate.ts` 里的 `U8()` 函数：每一个 step 的 `where` 字段都可能挂一条路径，T1 卡五步里有三步带 `U8：… ⚠️ 待实机核对`。一张卡三条灰色小字路径，全带警告标。这是三重噪音：

① 路径太多 → 她不知道现在该看哪条；
② 全带 ⚠️ → 警告标失去意义，看多了就自动忽略，等于没标；
③ 更糟的是 —— **她照着一条 ⚠️ 的路径点进去发现没有，会开始怀疑这个软件所有的话**。SPEC-product R3 原话："一次幻觉毁掉全部信任。"

**【小采】** 那你的方案是什么？不印？

**【苏姐】** 印，但按三条规则收敛：

**规则 A · 一张卡最多一条路径条。** 只印 `primaryAction` 那一步的路径（第 3 轮定的：主操作唯一）。其余步骤的路径收进展开区的 hint。理由：她卡在哪一步，主操作就在哪一步，其余路径此刻对她没用。

**规则 B · 三态三形，不许混。** 复用 `src/tutorial/content.ts` 已有的 `Confidence` 三值，一条路径必须携带它：

| confidence | 呈现 | 交互 |
|---|---|---|
| `verified` ✅ | 灰底路径条：`U8 › 采购管理 › 采购订单 › 增加` | 右侧 `[看图文]` 跳教程 |
| `unverified` ⚠️ | 同上 + 尾部橙色徽章 `待你核对` | 点徽章展开一行：`这条路径对吗？ [对，就是它] [不对，我改 ___]` |
| `unknown` ❌ | **不显示任何路径**，显示一行：`这一步在 U8 哪儿做，我还没核实过 → [问采姐] [去核对]` | 绝不编造 |

**【小采】** 规则 B 的 ❌ 那一档**我不同意**。"我还没核实过"这句话对她是没有帮助的 —— 她还是不知道去哪儿。我在带教里从来不说"我不知道"就结束，我说"我不知道，但这件事去问谁能问到，第一句话这么说"。

改成这样：❌ 档不显示路径，但**必须显示"找谁问 + 开口第一句"**，并且这句话直接从 `OPEN_QUESTIONS` 的 `howToVerify` 生成。比如：

```
这一步在 U8 哪儿做我还没核实过。
→ 问老采购一句：「X 姐，采购管理展开后有哪几个二级节点？我截个图记一下。」
   [复制这句]  [问采姐]
```

**【苏姐】** 这个补充我完全接受，而且它比我原来的版本强 —— 它把"系统缺陷"转成了"一次跨部门沟通的机会"，正好接上 SPEC-product §6 砍第 6 项那个思路（"内容她自己长出来，顺手把公司五问的待验项回填了"）。

**规则 C · ⚠️ 的核对结果要能沉淀。** 她点了 `[对，就是它]`，这条路径的 confidence 就该从 `unverified` 升 `verified`，**全局生效**，以后所有卡片上这条路径都不再带警告。这是把 SPEC §附「待实机核对项汇总」从一份没人填的清单，变成她干活顺手就填完的东西。

**【小采】** 这个我举双手赞成，但它有成本 —— 要落一张 `u8_path_verification` 表，要在设置页做回填入口，要处理"她改错了怎么撤回"。一小时预算够吗？

**【苏姐】** 不够。所以这一版做**半个**：`[对，就是它]` / `[不对，我改]` 的结果**只记在这张卡上**（写进 `note` 与一条 `taskEvent`），不做全局回写。全局回写和设置页回填进停车场，下一版做。这是等价交换，写进砍掉清单。

**【小采】** 接受。那和 21 篇教程怎么联动？现在教程有 `id`、有 `stage`（plan/order/confirm/track/receive/settle/basics），卡片有 `kind`。

**【苏姐】** 两条通道，一主一辅：

**主通道 · 卡片 → 单篇教程（精确）。** 按 `kind` 定一张写死的映射表 `TUTORIAL_OF[kind]`，指到具体那一篇。这是"我现在这件事的说明书"，不许模糊匹配、不许算法推荐 —— 21 篇是有限集，手写一张表最可靠。

**辅通道 · 泳道 → 教程分组（浏览）。** 教程 `stage` 与看板泳道对齐一张表，她在某条泳道点"这一类活怎么干"，进教程页时**自动筛到对应分组**。`plan` 和 `order`、`confirm` 三个 stage 合并映到「待下单」，`track` → 「在途」，`receive` → 「入库」，`settle` → 收工清单，`basics` → 不归任何泳道，常驻。

**【小采】** 主通道那张表我来定，我按"她卡在这件事时最该看哪一篇"来定，不按"名字像"来定。有两个要注意：

- T1_shortage 我给 `net-requirement` 而不是 `po-essentials`。理由：她在下单卡上最容易错的不是"订单要写哪九项"，是"这个数算对没有"。九项那篇挂 `related`。
- T7_not_stocked 我给 `po-instock-query`，因为那篇标题第一句就是"入库单在库存管理，不在采购管理"—— 这正是她找不到的原因。

**【苏姐】** 还有一条兜底：**教程本身 confidence 是 `unknown` 的，卡片上不显示 `[看图文]` 链接**，改成显示那篇的 `OPEN_QUESTIONS` 条目。不能把她引到一篇同样说不清的文章里去 —— 那比不给链接更伤信任。

**【本轮结论】**
U8 指引三条规则：**A 一卡一路径**（只印 primaryAction 那一步，其余收展开区）；**B 三态三形**（✅ 路径条+看图文 / ⚠️ 路径条+`待你核对`徽章+就地核对 / ❌ **不印路径**，改印「找谁问 + 开口第一句 + 复制按钮」，文案取自 `OPEN_QUESTIONS.howToVerify`）；**C 核对结果沉淀** —— 本版只记在卡上（`note` + `taskEvent`），全局回写与设置页回填进停车场（等价交换见砍掉清单）。
教程联动两条通道：**主通道** `TUTORIAL_OF[kind]` 手写映射表（精确，21 篇有限集，不做算法推荐）；**辅通道** 教程 `stage` → 泳道分组筛选（plan+order+confirm → 待下单，track → 在途，receive → 入库，settle → 收工，basics → 常驻）。教程自身 `confidence = unknown` 时不给 `[看图文]`，改给该篇的 `OPEN_QUESTIONS`。全表见 §最终方案 · 4。

## 第 6 轮 · 知识库「按模块」怎么分？

**【苏姐】** 现状：`taxonomy.ts` 里 40 个主题，`classify.ts` 里 10 个分类，`KnowledgePanel.tsx` 首屏一次铺开。用户原话："知识库的体系要按照模块来，不要上来就是大的列表。"

我先说我的方案：**按岗位场景分**。四个模块：「我要买东西」「我要跟货」「我要收货」「我要报账」。理由是场景语言比分类语言更接近她的心智 —— 她不会想"我要看下单与算量分类"，她会想"我今天要买东西"。

**【小采】** **我不同意。** 你这四个场景名，和我们刚在第 2 轮辛辛苦苦定下来的四条泳道，是**两套不同的词**说**同一件事**。

她一天要在这两处之间来回跳：看板上写「待下单」，知识库里写「我要买东西」。她得在脑子里做一次翻译。这是白白多出来的认知成本，而且是**每天都要付的**。

我的方案：**知识库模块名 = 看板泳道名，一字不差，颜色也一样。** 她在「待下单」道卡住了，点进知识库看到的第一张卡也叫「待下单」，同一个色。零翻译。

**【苏姐】** ……这一条我服，而且我该早想到 —— 这正是我自己一直讲的"不要做功能，要做场景"，只不过这里的"场景"最强的表达就是"她现在在哪条泳道上"。

但四个模块装不下 40 个主题，特别是 `finance.*` 和 `policy.*` 那些，它们不属于某一条泳道，是横切的。

**【小采】** 所以是 **4 + 2**：四个泳道模块，加两个常驻模块。

- **① 需求与算量**（对齐「需求」道）
- **② 下单与回签**（对齐「待下单」道）
- **③ 在途与催货**（对齐「在途」道）
- **④ 到货与入库**（对齐「入库」道）
- **⑤ 钱与票**（常驻，不属于任何一天的某一刻，但月底一定用得上）
- **⑥ 规矩与底线**（常驻，红线、留痕、廉洁、角色边界 —— 这一类不是"要用的时候查"，是"必须先知道"）

前四个和泳道同名同色，后两个用中性色，视觉上就区分开"跟着今天的活走"和"随时该知道"。

**【苏姐】** 那 `u8.*` 那 4 条主题（登录账套、现存量查询、订单录入、参照生成）放哪？我的意见是**单独立一个「系统操作」模块**，因为 U8 是她最大的短板，值得一个显眼的门。

**【小采】** **我不同意，这是我今天最后一次不同意。** 理由有两层：

第一层，**她的问题从来不是"我要学 U8"，是"我这一步在 U8 哪儿做"**。你给她一个 U8 模块，她进去看到四条主题，还是不知道该看哪条 —— 因为她的检索起点是业务动作，不是系统功能。这一点在 `src/tutorial/content.ts` 顶部的注释里已经被验证过一次了，原文：「教程不再按'软件功能'分组，改按采购闭环的阶段…新人打开教程时问的不是'我要用哪个功能'，而是'我现在卡在这一步，该看哪篇'」。教程已经这么改过了，知识库没理由退回去。

第二层，**U8 教程已经是一个独立的一级入口了**（`TutorialView`，21 篇）。你在知识库里再立一个 U8 模块，就有两个门通向同一片地，她每次都要猜该走哪个。

**【苏姐】** 那 u8 那 4 条主题怎么办？

**【小采】** 拆进阶段模块：`u8.stock-query` → ①（查现存量是算量的第一步）；`u8.po-entry` → ②；`u8.reference-generate` → ④（参照生成的坑集中在到货→入库那一段）；`u8.login-account` → ⑥（登录账套属于"必须先知道"）。知识库模块卡上不提 U8 三个字，但每条主题里该带的 U8 路径照带。

**【苏姐】** 成交。那**首屏到底显示什么**？这是用户那句"不要上来就是大列表"的正面回答，必须说死。

我的答案：**首屏只有 6 张模块卡，一个主题名都不出现。** 每张卡三行：

1. **模块名**（+ 泳道同色左边条）
2. **一句进度**：`齐了 7 / 共 9 条` + 一根细进度条
3. **一句后果**：这个模块里**缺失的、required 的、排第一条**的那个主题的 `why` 摘要 —— 不是"你还缺 2 条"，而是"**缺：可用量口径。照现存量算缺口会少下单，开线才发现料被别人领走了**"

第 3 行是这个设计的灵魂。40 条主题一次铺开的问题不是"太长"，是"**每一条看起来都一样重要，所以每一条都不重要**"。模块卡只讲最疼的那一条，她就知道该先补哪个。

**【小采】** 第 3 行我要加一个约束：`required = false` 的主题**永远不上首屏**。SPEC 里 `taxonomy.ts` 的注释原话："required 只给缺了会直接做错事、赔钱、被审计的主题…否则一个新库开机就是四十条红字，人就直接把提醒关了。" 首屏那句后果只允许来自 required 缺失项；一个模块的 required 全齐了，第 3 行改成一句肯定：`必备的都齐了 · 还有 3 条建议项`。

**【苏姐】** 收。**进去之后看到什么**：

一屏两段，不分页：

- **上段「先补这几条」**：该模块内 `required && 缺失` 的主题，最多 3 条。每条：主题名 + `askIfMissing`（去要哪份文件、找谁要）+ `[记一笔]`（她要到了就标齐）。
- **下段「这个模块里的全部主题」**：其余主题一行一条，折叠态，只显示 主题名 + 状态徽章（齐 / 缺 / 弱）。点开才显示 `why` 与关联。

关联里 **`contrast`（易混对照）单独提到最上面，用醒目样式**。`taxonomy.ts` 注释里写得很清楚："contrast 对新人最值钱——现存量 ↔ 可用量、到货 ↔ 入库、请购单 ↔ 采购订单这种，错一次就是一次事故。"

**【小采】** 最后一件事：**搜索框要在首屏顶部常驻，且搜索结果绕过模块直接给主题**。模块是浏览路径，不是牢笼 —— 她要是已经知道自己找"暂估"，不能逼她先猜暂估在哪个模块里。

**【苏姐】** 同意。模块**固定 6 个，不可自定义、不可增删** —— 这条也写进砍掉清单。一旦允许自定义，模块名和泳道名的对齐就守不住了，而对齐是这套设计的全部价值。

**【本轮结论】**
知识库分 **4 + 2 = 6 个模块**：四个**与看板泳道同名同色**（需求与算量 / 下单与回签 / 在途与催货 / 到货与入库），两个常驻中性色（钱与票 / 规矩与底线）。
**不设「系统操作 / U8」模块** —— 她的检索起点是业务动作不是系统功能（教程已在 2026-09-04 做过同样的重组），且 U8 教程已是独立一级入口，两个门通向同一片地会让她每次都要猜。`u8.*` 4 条主题拆进阶段模块。
**首屏只有 6 张模块卡，零主题名**。每卡三行：模块名 / `齐了 N/M 条`+进度条 / **最疼的那一条 required 缺失项的后果原文**（required 全齐则改为肯定句）。
进入模块后一屏两段：上段「先补这几条」（required 缺失，≤3 条，带 `askIfMissing` 与找谁要）+ 下段全部主题折叠列表；`contrast` 关联提到最上面用醒目样式。搜索框首屏常驻且绕过模块直达。模块**固定 6 个不可自定义**。

## 1. 四泳道定义表

划界判据一句话：**看现在是谁在动。**

| # | 泳道名 | `stage` 值 | 现在谁在动 | 她的姿势 | 覆盖状态机（SPEC §5） | 进入条件（可程序判定） | 离开条件 |
|---|---|---|---|---|---|---|---|

| ② | **待下单** | `to_order` | **她自己** | 这件事今天动不动，完全取决于我 | S2 · S3 | 数量已定、编码已定、最晚下单日已算出且 ≥ 今天 | **拿到书面回签**（含数量 + 每批到货日）→ 转 ③ |
| ③ | **在途** | `transit` | 供应商 + 物流 | 我只盯、只催，不做 | S4 · S5 · S5x | `signed_back_at` 非空 且 未到数量 > 0 | 货到本地（有送货单/到货登记）→ 转 ④ |
| ④ | **入库** | `inbound` | 仓库 + 质检 | 我核对、我定性，实操是他们 | S6 · S6x · S7 | 货已到本地，或明日到货预告已生成 | `累计入库增量 = 实到量` 且差异已定性 → 关闭 |

**边界上的三条裁决**

1. **「未回签」归 ②「待下单」**，不归 ③。依据 SOP 03 第三步第 4 点「回签前订单只是你的一厢情愿」+ 口诀「无签不认」。放 ③ 的直接危害：她会把未回签的量当**有效在途**扣减净缺口（SPEC §7 盲区第 2 条），缺口算小 → 到需求日两头空。
2. **T6 明日到货预告归 ④**，虽然发生在货到之前 —— 它是入库这件事的第一步（SOP 04 第一步），完成判定是「仓库回执」，动的人是仓库。
3. **①「需求」道的卡片积压率单独统计**，不并入 SPEC-product §1 反指标「卡片积压率 > 30%」的全局口径。理由：这一道的闭环天然不由她说了算，混算会让反指标持续误报，最后没人看它。

### 三档 × 分数的分工

| | `band` 三档 | `score` 0~200 |
|---|---|---|
| 回答什么问题 | 这件事**是什么性质**、我该拿什么姿势 | 同性质的几件事**谁先做** |

**「今天三件事」横幅取消** —— urgent 分区本身就是横幅，一屏两处置顶是重复（见砍掉清单第 2 项）。

## 3. 卡片信息架构

### 3.1 三层字段清单

**① 事实层 · 永久只读**（来源 U8 / 生产表，每个字段旁常驻来源戳）

| 字段 | 中文 | 来源 | 为什么不能写 |
|---|---|---|---|
| `materialCode` | 货码（存货编码） | U8 存货档案 / 生产表 | 全局主键。改它 = 这张卡换了个物料，打分因子（日均用量/覆盖天数/准交率）静默全变 |
| `qty` | 订单数量 | U8 采购订单 | **三单匹配第一条腿**（SOP 01 §1.3），改了付款风控没基准 |
| `receivedQty` | 到货数量 / 累计到货 | U8 订单执行报表 | 三单匹配第二条腿 |
| `stockedQty` | 入库数量 / 累计入库 | U8 订单执行报表 | 三单匹配第二条腿；SOP 05「以 U8 为准，不维护第二套账」 |
| `netGap` | 净缺口 | 系统算（`calc_order_qty`） | 系统算的，算式可展开（ⓘ 保留），不可手改 |
| `available` | 可用量 | U8 现存量查询 | SPEC §7 盲区第 1 条，手改就是自欺 |
| `price` / `taxIncluded` | 单价 / 含税口径 | U8 价格档案 | 差 13% 的地方（SPEC §7 盲区第 5 条） |
| `poStatus` | 订单状态（开立/已审核/关闭） | U8 | 保存 ≠ 生效，状态是 U8 的事实 |
| `needDate` | 需求日期 | 生产表 | 生产给的需求。改它 = 替生产改需求（越权）。要改走 T3 拦截卡要书面 |

**② 判断层 · 可写，不覆盖事实层，并列显示**

| 字段 | 中文 | 谁承诺的 | 参与打分？ | 说明 |
|---|---|---|---|---|
| `materialCodeFix` | 人工核定货码 | 她核实后 | ❌ | 不改 `materialCode`；`[用这个]` 生成 `T14_conflict` 卡 |
| `supplierOverride` | 本单实际供应商 | 她的决定（启用备选） | ❌ | 不改物料档案主供应商 |
| `promiseDate` | 承诺到货日 | **供应商** | ✅ **仅当** `promiseSource = signback` | 跟货类任务的最晚动作日锚点（SPEC §3.1 f_time） |
| `promiseSource` | 承诺来源 | — | — | 枚举 `signback` / `verbal` / `guess`。填 `verbal`/`guess` 时界面明示「这个日期不会进打分，因为它还不是书面承诺」 |
| `etaDate` | 物流预计到达 | 物流 | ❌ | U8 不记物流 |
| `trackingNo` | 物流公司 + 运单号 | 供应商 | ❌ | 「已发货」必须三样齐（SPEC §7 盲区第 17 条） |
| `nextActionAt` | 明天几点再动 | **她自己** | ❌ | SPEC §4 清单第 2 条「允许未闭环，不允许没交代」 |
| `blockedBy` | 卡在谁那里 | 她判断 | ❌ | 枚举 none/warehouse/finance/production/supplier |
| `escalatedTo` | 已升级给谁 | 她的动作 | ❌ | |

> **日期可写判据**：**这个日期是谁承诺的，就只有拿到那个人的承诺才能写。** 供应商的（`promiseDate`）、物流的（`etaDate`）、她自己的（`nextActionAt`）可写；生产的（`needDate`）不可写。

**③ 过程层 · 可写，自由**

| 字段 | 中文 | 说明 |
|---|---|---|
| `note` | 备注 | 自由文本，不参与任何计算 |
| `taskEvent[]` | 跟进记录 | 一条 = `日期 + 渠道 + 对方姓名 + 原话 + 结论 + 新承诺日`（SPEC §6.7 `task_event`）。扯皮时的证据链 |

1. 模块名（①②③④ 带泳道同色左边条，⑤⑥ 中性色）
2. `齐了 N / 共 M 条` + 进度条
3. **最疼的那一条的后果原文**：该模块内 `required = true && 缺失` 的主题，按 `SEEDS` 声明顺序取第一条，显示 `缺：{name} —— {why 前 40 字}`。**`required = false` 的主题永不上首屏**（依据 `taxonomy.ts` 注释：否则开机就是四十条红字，人直接把提醒关了）。required 全齐 → 改为 `✅ 必备的都齐了 · 还有 K 条建议项没补`。

### 5.3 进入模块之后

一屏两段，不分页：

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  ‹ 返回     ▌需求与算量                              齐了 5 / 共 7 条         │
├──────────────────────────────────────────────────────────────────────────────┤
│  先补这两条（不补会直接出事）                                                │
│  ┌────────────────────────────────────────────────────────────────────────┐  │

│  │ …                                                                       │  │
│  └────────────────────────────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────────────────────────────┤
│  这个模块里的全部主题                                                        │
│   ✅ 净缺口怎么算                                                        ▸   │
│   ✅ 现存量查询（U8）                                                    ▸   │
│   ✅ 存货编码规则                                                        ▸   │
│   🟡 计量单位与换算（只有一处提到，算「弱」）                            ▸   │
│   ✅ 替代料                                                              ▸   │
│   ⚠️ 可用量口径                                                          ▸   │
│   ⚠️ 交期倒推日历口径                                                    ▸   │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **上段「先补这几条」**：`required && 缺失`，最多 3 条。每条 = 主题名 + `why`（不补会怎样）+ `askIfMissing`（找谁要、要哪份文件）+ `[复制这句]` + `[记一笔]`。
- **下段「全部主题」**：其余一行一条，折叠。状态徽章三值：`✅ 齐`（命中 ≥ `minChunks`）/ `🟡 弱`（命中但不足 `minChunks`）/ `⚠️ 缺`。
- 展开一条后，**`contrast`（易混对照）关联提到最上面用醒目样式** —— 依据 `taxonomy.ts` 注释：「contrast 对新人最值钱，错一次就是一次事故」。`prerequisite` / `downstream` / `same-doc` 三类排其下，弱化。
- **搜索框首屏常驻且绕过模块直达主题** —— 模块是浏览路径，不是牢笼。
- **模块固定 6 个，不可自定义、不可增删**（见砍掉清单第 7 项）。

## 5. 验收（每条可程序判定）

1. `bandOf()` 的 28 条规则每条至少一个正例 + 一个反例单元测试；`N7` 兜底测试：构造一张所有条件都不命中的卡，必须返回 `notice`。
2. 同一批卡任意打乱输入顺序，`rankTasks()` 输出完全一致（全序稳定性回归，沿用现有 `rules.test.ts` 思路）。
3. 构建期校验三条全部生效：`gate ≤ 2` 超限失败 / `doneRule` 无落点失败 / `confidence=unknown` 缺 `askScript` 失败。
4. `updateTaskFields()` 传入任一事实层字段名（`qty` `receivedQty` `stockedQty` `materialCode` `needDate` `available` `price` `netGap` `poStatus`）必须抛错。
5. `promiseSource ∈ {verbal, guess}` 时，`score` 与该卡 `promiseDate` 无关（改日期分数不变）。
6. `MODULE_OF_TOPIC` 覆盖 `taxonomy.ts` 全部 40 条主题，无遗漏、无一条属于两个模块。
7. 知识库首屏 DOM 里**不出现任何 `TopicSpec.name`**（用户"不要上来就是大列表"的可测判据）。

# 四、明确砍掉什么（一小时预算 · 等价交换）

> 规则（`references/prioritization-scope.md` §三）：任何新增 scope 必须伴随砍掉某项或明确延期。本版新增 = 三档分区 + 泳道重划 + 主操作模型 + 三层字段 + U8 三态 + 知识库六模块，对应砍下面 8 项。

| # | 砍掉 | 理由 | 去哪 |
|---|---|---|---|
| **1** | **P0/P1/P2/P3 四色分级的全部 UI**（`tier-*` 色带、分档角标、`levelText()` 的界面调用） | 三档取代它。同屏两套优先级语言 = 她要做两次翻译。`level` 字段留在数据层供日清与导出用，不上屏 | 永久砍 |
| **2** | **「今天三件事」顶部横幅 + `TOP_N` / `top3` 全套逻辑** | 🔴紧急分区本身就是横幅。一屏两处置顶是重复，而且会出现「横幅里三张 + 紧急区里五张」的矛盾观感 | 永久砍 |
| **3** | **卡片附件上传**（回签件图片/PDF、差异照片、加单微信截图） | 要做文件选择、存储、缩略图、清理，一小时装不下。本版 `evidence` 只存**路径文本或一句描述**，她自己知道文件在哪 | 停车场（下一版） |
| **4** | **`materialCodeFix` / `supplierOverride` 回写物料表** | 自动改数据源违反铁律 5（"她背的锅必须由她按的按钮产生"）。本版只并列显示 + 生成 `T14_conflict` 卡提醒她去源头改 | 永久砍（自动回写），核对卡保留 |
| **5** | **U8 路径核对结果的全局回写与设置页回填入口** | 要落 `u8_path_verification` 表 + 设置页 UI + 撤回逻辑。本版 `[对，就是它]`/`[不对，我改]` **只记在本卡** `note` + 一条 `taskEvent` | 停车场（下一版）——这是第 5 轮里明确记账的一次等价交换 |
| **6** | **知识库模块的自定义**（增删模块、改名、拖主题） | 一旦可自定义，模块名与泳道名的对齐就守不住，而对齐是这套设计的全部价值。6 个模块写死在 `modules.ts` | 永久砍 |
| **7** | **卡片的 `[怎么做]` 按钮** | 行为与点标题展开完全相同，是个冗余按钮。卡面按钮从 3 个减到 2 个（主操作 + 问采姐） | 永久砍 |
| **8** | **`T11` 月度对账进泳道** | 月度粒度进不了日看板。只把它的日粒度切片拿出来做 `T13_payment`（付款/开票节点 ≤ 明天才生成）。T11 本体仍只在收工清单的月末追加项里 | 永久砍（本体不进泳道） |

**继续沿用 SPEC-product §6 已砍的 6 项**（拖拽看板 / 向量检索 / U8 直连写回 / 学习计划测验打分 / 云同步 / 教程录屏 GIF），本版不复活任何一项。

**停车场（好想法，不在本期）**
- U8 路径核对的全局沉淀 + 设置页「公司五问」回填（砍 5）
- 卡片附件与凭据文件管理（砍 3）
- `band` 判定规则的用户可调（她说"这类我不认为紧急"→ 记规则）
- 供应商合并沟通卡（`R2 groups` 已有数据，本版只显示提示不做合并卡）
- 知识库模块进度 → 学习计划的自动排课
- `T13_payment` 的付款节点自动推算（本版要求手工填月结到期日）

**假设（若不成立本方案要回退）**
1. 她愿意在卡片上填凭据字段（订单号、新交期）—— 若不愿，`executePrimaryAction` 的 required evidence 要降为 0 个，退回一键完成。
2. U8 五问在两周内至少回填 2 项 —— 若一项都填不上，⚠️ 会占到路径条的 90%，警告标失效，那时要改成「默认不显示路径，点了才展开」。
3. 40 条主题的 `required` 标注基本准确 —— 首屏第 3 行完全依赖它，标错了首屏就在喊错的话。

**Non-goals（本版明确不做）**：多用户 / 云同步 / 移动端 / U8 直连与写回 / 语音 / 供应商门户 / 比价寻源 / 合同与付款管理 / KPI 报表 / 看板视图自定义。
